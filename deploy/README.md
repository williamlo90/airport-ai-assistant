# Release package — Westbridge Airport

This package targets Kubernetes with external Neon. `base/` contains a same-pod HTTPS nginx frontend and loopback API. Only port443 is exposed through the Service. Certificates and all credentials are provisioned separately; no Secret values or external hostname are committed.

Build from the repository root with `docker buildx build --platform linux/amd64 --load -f deploy/containers/backend.Dockerfile -t westbridge-backend:release-candidate .` and repeat serially for frontend/reference. Use a dedicated docker-container builder with `deploy/containers/buildkitd.toml`, memory1536m and CPU quota100000/period100000; do not start Docker Desktop automatically on the owner's workstation. Image digests are recorded after actual builds, not inferred from Dockerfiles. Registry base digests are pinned in `base-images.json`.

The backend image contains installed non-editable Python packages, including Alembic revisions and SQL resources. Runtime roles differ: API gets only `westbridge-api` (DATABASE_URL pooled, SESSION_SECRET, SOURCE_API_BASE_URL, SOURCE_API_TOKEN, SOURCE_CONTEXT_SECRET, SOURCE_TENANT_MAP); worker gets only `westbridge-worker` (WORKER_DATABASE_URL); migration gets only `westbridge-migration` (DATABASE_DIRECT_URL direct). The database's dedicated runtime/policy/auth/worker/job-owner roles must be provisioned with the existing audited setup commands before rollout. Tenant hosts, membership, provider routes and knowledge are configuration/data setup, not invented by a migration or image build.

Create namespace `westbridge` and TLS secret `westbridge-tls` out of band. Render `kubectl kustomize deploy/kubernetes/migration`, set the exact built backend digest, run the unique migration Job and wait for completion BEFORE rendering/applying `deploy/kubernetes/base`. Migration is deliberately absent from base; it is not an initContainer and has backoffLimit0. A failed migration blocks rollout. Never run migrations using a production credential during package qualification. The package proof uses an isolated disposable schema and installed resources from a clean candidate checkout.

Before deployment replace all release-candidate image tags with built immutable digests. No apply/provisioning occurs in RELEASE-01. Kubernetes distribution, external routing/domain, host capacity and budget belong to RELEASE-02. A one-node cluster is not cross-machine HA.

Baseline flags disable commercial AI and all email; worker replicas0 intentionally cannot claim/send jobs. Activate each capability only with its reviewed secrets/config and authorized testing scope. Disabled retrieval/AI and missing email are not claimed as a working full product deployment. ClamAV must be installed in the API pod (current adapter uses loopback), configured with explicit scanner port, then verified under RELEASE-02 before uploads are accepted. Production forbids AMSI. Official ClamAV guidance recommends minimum3GiB; do not run that engine locally under the lightweight packaging budget. Attachment access remains fail-closed while scanner is unavailable.

`/health/live` checks process. `/health/ready` performs only a bounded2s core database SELECT1; it does not promise provider/source/scanner health. The API listens only127.0.0.1 and trusts forwarded headers only from127.0.0.1. Nginx terminates TLS and overwrites client forwarded headers; public host+origin remain checked by the application. Full TLS/cookie/CSP/browser/rollback acceptance is FE-DEPLOY-01/RELEASE-02, not inferred from rendering manifests.

The optional reference image uses environment-only configuration and a separately provisioned read-only SQLite path. It contains fictional fixture definitions, not a ready database, token or .env. Its HTTPS source endpoint/storage lifecycle is configured in RELEASE-02.

`python scripts/release/package.py check` performs offline package checks. `checkout --destination local/team/release-01/candidate` makes an isolated Git snapshot/clean clone of current public candidate files, including allowlisted untracked implementation files. It does not stage/commit/change the workspace index or publish anything. The candidate commit differs from the workspace's stale HEAD and is identified explicitly in evidence.
